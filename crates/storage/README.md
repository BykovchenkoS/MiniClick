# Storage

Крейт реализует MergeTree через `types::Table` и `types::TableFactory`.
Ядро синхронное; HTTP, SQL и сохранение описаний таблиц относятся к другим крейтам.

## Использование

`MergeTreeFactory` создаёт `Arc<dyn Table>` по `TableDefinition`.
`MergeTreeTable::open(&definition, data_dir)` возвращает конкретную таблицу.
`data_dir` — каталог **одной таблицы**; дополнительный каталог с её именем
фабрика не добавляет. Engine должен быть MergeTree, ORDER BY — непустым.

- Один непустой INSERT создаёт один отсортированный неизменяемый part.
  Пустой корректный блок ничего не меняет. Схема блока проверяется полностью.
- `scan` возвращает ленивый поток гранул со снимком выбранных parts.
  Колонки идут в порядке `ScanRequest.columns`. Пустой список колонок сохраняет
  число строк без чтения `.bin`.
- Predicate используется только для консервативного отсечения.
  Точный WHERE применяет Query; лишние строки внутри выбранных гранул допустимы.
- `explain_scan` использует тот же выбор parts и гранул, без чтения колонок.
  `rows_selected` — число строк до точной фильтрации.
- `optimize` последовательно сливает соседние parts, пока не останется один.
  На один merge приходится до четырёх входных гранул и одна выходная в памяти.
  Повторяющиеся строки сохраняются. Глобальная сортировка обычного scan
  между разными parts не гарантируется.
- `flush` синхронизирует каталог на Unix; файлы синхронизируются при записи.
  На Windows синхронизация каталога пропускается с проверкой существования
  каталога: устойчивость переименований к отключению питания не гарантируется.
  Проверки обычного рестарта и аварийного завершения процесса не доказывают
  сохранность данных при отключении питания.
  `drop_data` удаляет каталог и инвалидирует старую таблицу и её читателей.
- `parts` возвращает отсортированные имена активных parts.
  `export_part` и `sync_parts` пока возвращают `Unsupported`.

Изменения сериализуются внутри таблицы. Читатели не удерживают блокировку
на время чтения колонок. Блокировка `.lock` запрещает повторное открытие
каталога, пока таблица или её читатели ещё живы. Используется файловая блокировка
из стандартной библиотеки Rust, доступная начиная с Rust 1.89.

## Формат и восстановление

Каждый part содержит `part.json`, `primary.idx`, `<column>.bin` и `<column>.mrk`.
Бинарный формат — little-endian, версия метаданных — 1.

- Рамка `.bin`: кодек u8, сжатый размер u32, исходный размер u32, данные.
  Кодеки: None = 0, LZ4 = 1, ZSTD = 2. Каждая гранула сжимается отдельно.
- Метка `.mrk`: смещение u64 и число строк u32, всего 12 байт.
- `primary.idx`: значения первых строк гранул, колонка ключа за колонкой,
  без сжатия.
- Числа записываются фиксированной шириной; String — длина u32 и UTF-8.
  Date занимает 4 байта, остальные числовые типы — 8.
- Ключи Float64 в JSON записываются как `{"float64_bits": <u64>}`:
  это сохраняет точность, знак нуля, бесконечности и биты NaN.
- Несжатый размер одной рамки ограничен 256 МиБ. Повреждённые размеры,
  метки, несовместимые схемы и версии приводят к ошибке без паники.
  Контрольные суммы пока не реализованы; формат не обнаруживает все битовые ошибки.

`table.json` хранит счётчик вставок, описание таблицы и список активных parts.
Имена имеют вид `all_<min>_<max>_<level>`; номера резервируются до записи
и не переиспользуются после ошибки. Настройку кодека можно изменить при открытии:
старые рамки читаются по собственному заголовку. Схема, ключ и размер гранулы
должны совпадать с сохранённым описанием.

Запись part идёт через `tmp_<name>` с переименованием. Новый активный набор
публикуется переименованием временного `table.json`. До публикации merge
активны исходные parts, после — результат. Старые parts удаляются после
освобождения последнего читателя. При запуске активный набор восстанавливается
из `table.json`, временные и неактивные каталоги удаляются. Если каталог содержит
parts без `table.json`, открытие возвращает ошибку вместо догадки об активном наборе.

## Проверки

```bash
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo test --release -p storage --test lifecycle million_rows -- --ignored --nocapture
```

Модульные тесты лежат рядом с кодом в `mod.rs` / `tests.rs`, интеграционные —
в `tests/`. Проверяются все типы ключей и кодеки, пропуск повреждённых гранул,
атомарность при ошибках записи, параллельные операции и аварийный выход процесса
до и после публикации merge. Проверка миллиона строк запускается отдельно.
