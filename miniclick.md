# MiniClick

Учебная колоночная СУБД на Rust по мотивам ClickHouse: HTTP-интерфейс, SQL, хранение MergeTree.

В этой лабе делаем всё, кроме репликации, и сдаём локально работающий исполняемый файл с веб-интерфейсом Swagger. Репликация — следующая лаба; под неё сейчас только заготовки в коде.

Документ из двух частей. Первая — общие положения, о которых договариваемся вместе до начала работы. Вторая — три блока, которые три человека делают параллельно, у каждого блока шаги идут по порядку.

Код общей части лежит в крейте `types` (архив miniclick-skeleton.zip). Он собирается и проходит тесты.

# Часть 1. Общие положения

## Что делаем

SQL:
- `CREATE TABLE t (...) ENGINE = MergeTree ORDER BY (...)`, также `ENGINE = Memory`;
- `DROP TABLE`, `OPTIMIZE TABLE`;
- `SELECT` с WHERE, GROUP BY, ORDER BY, LIMIT;
- агрегаты count, sum, min, max;
- `EXPLAIN SELECT ...` — план и сколько parts и гранул будет прочитано;
- без JOIN, подзапросов и UNION.

INSERT — через отдельный HTTP-запрос с телом в CSV, TSV или JSONEachRow, а не через SQL.

Типы колонок: Int64, UInt64, Float64, String, Date, DateTime. NULL пока нет.

## Что сдаём

Один исполняемый файл `miniclick`, собранный `cargo build --release` и запущенный на Linux (можно в WSL). Настройки — флагами командной строки или `config.toml` рядом, данные — в `./data`. При показе в WSL проект и данные держим внутри файловой системы WSL (`~/miniclick`), а не в `/mnt/c`: через `/mnt/c` диск в разы медленнее, и замеры покажут его, а не наш индекс.

Показываем через Swagger UI в браузере (`http://localhost:8123/swagger-ui`), плюс bash-скрипт с curl на случай, если что-то пойдёт не так.

Демо-сценарий:
1. Запустить сервер, открыть Swagger UI.
2. Создать MergeTree-таблицу, загрузить CSV на миллион строк (Swagger показывает кнопку выбора файла).
3. Выполнить SELECT с WHERE, GROUP BY, ORDER BY и агрегатами.
4. Показать, что запрос по ключу быстрее полного скана (время — из демо-скрипта), и `EXPLAIN SELECT ...` с числом выбранных parts и гранул.
5. Перезапустить сервер, показать, что данные на месте.
6. Вставить ещё пару раз, выполнить OPTIMIZE, показать, что parts стало меньше (`GET /tables/{name}` или EXPLAIN).

Сценарий проверяем целиком хотя бы за неделю до сдачи.

## Распределение

| Блок | Что | Крейты |
|---|---|---|
| A. Storage | MergeTree: формат файлов, запись и чтение parts, индекс, сжатие, merge | storage |
| B. Query | разбор SQL, вычисление выражений, планировщик, выполнение, агрегаты, анализ условий для отсечения | query, `types::key_condition` |
| C. Сервер | HTTP и Swagger, Catalog, форматы ввода и вывода, конфиг, генератор данных, замеры, демо, CI, сборка всего вместе | catalog, server |

Нагрузку выровняли так: самую хитрую часть отсечения (может ли условие выполниться на диапазоне ключей) делает B, потому что это логика выражений; инфраструктуру, которая нужна всем, делает C. Получается примерно поровну. Storage всё равно на критическом пути ко второму этапу, поэтому на него лучше поставить самого сильного.

Общая часть (крейт types) — у всех троих. Репликация (крейт replication) — следующая лаба. Под неё в каждом блоке отмечено, что дёшево сделать уже сейчас.

## Этапы

1. Всё работает через HTTP, таблицы в памяти. Проверяем, что интерфейсы удобные. Делать как можно раньше.
2. Таблицы в памяти заменяются на MergeTree. Данные переживают рестарт, индекс отсекает лишние гранулы.
3. GROUP BY, ORDER BY, merge, сжатие.
4. Демо: Swagger, генератор данных, сценарий целиком.

Следующая лаба: репликация на нескольких нодах.

После каждого этапа — короткий созвон: что в интерфейсах оказалось неудобным, поправить.

## Если не успеваем

Кто освободился раньше, помогает A: Storage на критическом пути. Чаще всего это C — например, пишет интеграционные тесты для storage или берёт кодеки.

Что можно выкинуть, и демо при этом останется полным:
- ZSTD (оставить LZ4);
- формат вывода Pretty;
- ввод TSV и JSONEachRow (оставить CSV);
- avg;
- `/help`.

Что выкидывать нельзя: сохранение на диск и рестарт, отсечение по индексу с EXPLAIN, GROUP BY с агрегатами, OPTIMIZE, Swagger.

## Решения

1. Ядро синхронное. Сервер на tokio, вызовы ядра оборачивает в `spawn_blocking`. Поток блоков — обычный `Iterator`.
2. Одна ошибка на проект — `DbError` в `types`.
3. Все общие трейты `Send + Sync`, методы берут `&self`. Таблицу одновременно читают и пишут из разных потоков, блокировки — внутри реализации.
4. В коде трейты без префикса I (`Table`, `Catalog`, `QueryEngine`), как принято в Rust. На схеме они по-прежнему `ITable` и т.д.
5. Имена таблиц и колонок регистрозависимые.
6. INSERT не идёт через QueryEngine. Сервер берёт таблицу из Catalog, разбирает тело по её схеме в Block и вызывает `Table::insert`.
7. DDL и OPTIMIZE идут через `QueryEngine::execute`.
8. Catalog хранит описания таблиц на диске и при старте открывает таблицы через фабрику по engine: MergeTree — storage, Memory — `MemTableFactory`.
9. SQL разбирает библиотека sqlparser-rs с диалектом ClickHouse, её версию фиксируем. Планировщик и выполнение пишем сами. Типы sqlparser не выходят за пределы крейта query.
10. Репликация: один лидер, остальные — реплики, единица репликации — part. Подробно — в разделе «Репликация».
11. HTTP-слой на axum. Это одна часть, а не «шлюз плюс роутер». Группы эндпоинтов со схемы (query, insert, метаданные, admin, позже replica) — обычные модули с функциями-обработчиками, без отдельных трейтов I*Api: у каждого была бы одна реализация, а для тестов уже есть заглушки уровнем ниже (MemCatalog, StubQueryEngine).
12. Сериализация двух видов. Данные (`.bin`, `.mrk`, `primary.idx`) — свой бинарный формат, little-endian, без внешних библиотек: нам нужно переходить к гранулам по смещению. Метаданные (`part.json`, описания таблиц в каталоге) — JSON через serde. Поэтому на типах в `types` (DataType, Value, ColumnDef, TableSchema, Engine, Codec, TableSettings, TableDefinition) стоит `Serialize, Deserialize`, и `types` зависит от serde.
13. Файлы при INSERT клиент кладёт прямо в тело запроса (`curl --data-binary @data.csv`), без multipart и без сохранения на диск. С файлами на диске работают только storage (parts) и catalog (описания таблиц), через стандартные `std::fs` и `std::io`.
14. Swagger UI через utoipa и utoipa-swagger-ui с фичей `vendored`: тогда страница Swagger вшита в бинарник, и при сборке ничего не скачивается из интернета. Описание API пишется атрибутами `#[utoipa::path]` над обработчиками.
15. Анализ условий для отсечения (`may_match`) лежит в `types::key_condition`, владелец — B. Storage только вызывает его на min/max part и на границах гранул. Сейчас там заглушка, которая всегда отвечает «может совпасть» — это корректно по контракту, просто ничего не отсекает.

## Workspace

```
miniclick/
  crates/
    types/        общая часть, меняем вместе
    storage/      блок A
    query/        блок B
    catalog/      блок C
    server/       блок C, собирает всё вместе
    replication/  следующая лаба
```

storage, query, catalog и replication зависят только от types и друг о друге не знают. server зависит от всех.

В общую часть попадает только то, что пересекает границу между блоками. Всё остальное живёт в крейте того, кто это использует, и меняется без согласования. Поэтому часть типов со схемы переехала:
- PartId, PartMeta, Mark, GranuleRange, а также репозиторий parts, кодеки, индекс, отсечение parts и merge — в storage;
- SelectQuery, QueryPlan, парсер, планировщик, исполнитель и трансформы — в query;
- форматы ввода и вывода и HTTP-обработчики — в server. IQueryApi, IInsertApi, IMetadataApi, IAdminApi и IDbServer становятся модулями сервера, а не интерфейсами. На схеме достаточно заменить «HTTP Server + Router» одним блоком «HTTP-слой (axum)» и подписать четыре API как группы эндпоинтов.

## Общие типы

**DataType и Value** — тип колонки и одно значение. Value нужен для литералов, min/max и ключей индекса. Date хранится как дни с 1970-01-01 (i32), DateTime — как секунды UTC (i64). `Value::compare` сравнивает только значения одного типа; Float сравнивается через `total_cmp`. `Value::parse(text, type)` разбирает текст в значение, `Value::cast(type)` приводит литерал к типу без потери смысла, `Display` печатает значение (даты как `2026-10-01` и `2026-10-01 13:05:09`). Эти три функции общие для B и C, подробности — в разделе «Литералы и типы».

**ColumnData** — данные одной колонки, enum с вектором на каждый тип. Строки пока `Vec<String>`.

**Block** — несколько колонок с именами. При создании проверяется, что длины колонок совпадают, а имена не повторяются. Число строк хранится отдельно, потому что блок может быть без колонок: `SELECT count() FROM t` ничего не читает, но строки посчитать надо.

**TableSchema и TableDefinition** — колонки в порядке объявления, а также всё из CREATE TABLE: engine, ORDER BY, размер гранулы (по умолчанию 8192), кодек (по умолчанию LZ4). `validate` проверяет общие правила, например что колонки из ORDER BY существуют.

**Expr** — выражение: колонка, литерал, унарная и бинарная операция, функция (агрегаты тоже функции, имя в нижнем регистре). Expr лежит в общей части, потому что через ScanRequest уходит в storage. Литералы в нём уже разобраны в Value: `Value::Int64(42)`, а не строка `"42"`.

## Интерфейсы

```rust
pub type BlockStream = Box<dyn Iterator<Item = Result<Block>> + Send>;

pub struct ScanRequest {
    pub columns: Vec<String>,     // какие колонки вернуть, в этом порядке; может быть пусто
    pub predicate: Option<Expr>,  // подсказка для отсечения parts и гранул
}

pub struct ScanStats {   // для EXPLAIN и логов
    pub parts_total: usize,     pub parts_selected: usize,
    pub granules_total: usize,  pub granules_selected: usize,
    pub rows_total: u64,        pub rows_selected: u64,   // строк в выбранных гранулах
}

pub trait Table: Send + Sync {
    fn definition(&self) -> &TableDefinition;
    fn insert(&self, block: Block) -> Result<()>;
    fn scan(&self, request: &ScanRequest) -> Result<BlockStream>;
    fn explain_scan(&self, request: &ScanRequest) -> Result<ScanStats>;   // только отсечение, без чтения
    fn flush(&self) -> Result<()>;
    fn optimize(&self) -> Result<()>;
    fn drop_data(&self) -> Result<()>;

    // для репликации; по умолчанию Unsupported, реализует только MergeTree
    fn parts(&self) -> Result<Vec<String>>;
    fn export_part(&self, name: &str) -> Result<PartData>;
    fn sync_parts(&self, add: Vec<PartData>, remove: &[String]) -> Result<()>;
}

pub trait TableFactory: Send + Sync {
    // открыть таблицу в data_dir; если данных нет — создать пустую
    fn open(&self, definition: &TableDefinition, data_dir: &Path) -> Result<Arc<dyn Table>>;
}

pub trait Catalog: Send + Sync {
    fn create_table(&self, definition: TableDefinition, if_not_exists: bool) -> Result<()>;
    fn drop_table(&self, name: &str, if_exists: bool) -> Result<()>;
    fn get_table(&self, name: &str) -> Result<Arc<dyn Table>>;
    fn list_tables(&self) -> Vec<TableDefinition>;   // по имени
}

pub enum QueryOutput {
    Rows { header: Vec<ColumnDef>, stream: BlockStream },  // SELECT
    Ok,                                                     // CREATE, DROP, OPTIMIZE
}

pub trait QueryEngine: Send + Sync {
    fn execute(&self, sql: &str) -> Result<QueryOutput>;
}

// анализ условия для отсечения (types::key_condition, владелец B)
pub struct KeyRange { pub min: Vec<Value>, pub max: Vec<Value> }   // по колонкам ключа, включительно
pub fn may_match(predicate: &Expr, key_columns: &[String], range: &KeyRange) -> bool;

// репликация
pub struct PartData { pub name: String, pub files: Vec<(String, Vec<u8>)> }

pub trait Peer: Send + Sync {
    fn ping(&self) -> Result<()>;
    fn list_tables(&self) -> Result<Vec<TableDefinition>>;
    fn list_parts(&self, table: &str) -> Result<Vec<String>>;
    fn fetch_part(&self, table: &str, part: &str) -> Result<PartData>;
}
```

| Интерфейс | Реализует | Вызывает |
|---|---|---|
| Table | A (MergeTree), types (MemTable) | B (scan, explain_scan), C (insert), replication |
| TableFactory | A, types | C (catalog) |
| Catalog | C | B, C, replication |
| QueryEngine | B | C |
| may_match | B | A |
| Peer | C (по HTTP), types (LocalPeer) | replication |

## Договорённости, которых не видно из сигнатур

1. predicate в ScanRequest — только подсказка. Storage может вернуть лишние строки, но не может потерять подходящую. Query после scan всегда сам применяет фильтр. Поэтому Query работает с MemTable, которая predicate игнорирует, а storage может добавлять отсечение постепенно.
2. scan возвращает колонки ровно из `request.columns`, в том же порядке. Блоки в потоке могут быть любого размера, в том числе пустые.
3. В insert приходит блок, колонки которого совпадают со схемой по именам, типам и порядку. Приводит данные к этому виду сервер; таблица только проверяет и при несовпадении отвечает `TypeMismatch`.
4. Один вызов insert — одна атомарная вставка: после ошибки в таблице не остаётся части данных.
5. Заголовок результата SELECT лежит в `QueryOutput::Rows` и известен до чтения потока. Без этого нельзя вывести заголовок для пустого результата.
6. После `drop_table` таблицей не пользуются. Если на неё ещё кто-то держит `Arc` (идёт scan), реализация не должна падать — достаточно вернуть ошибку.
7. `may_match` консервативен: `true` значит «может быть», `false` — «точно нет». Ошибиться в сторону `true` можно всегда, в сторону `false` — никогда, иначе потеряются строки.
8. В `ScanRequest.predicate` литерал, который сравнивается с колонкой, уже приведён к типу этой колонки, если это возможно без потери смысла (раздел «Литералы и типы»). Если типы всё-таки разные, `may_match` отвечает `true`.
9. `explain_scan` и `scan` используют одно и то же отсечение, поэтому EXPLAIN всегда показывает ровно то, что будет прочитано. `explain_scan` данные не читает, только `part.json`, `primary.idx` и `.mrk`, которые уже в памяти.
10. `sync_parts` атомарен: scan видит либо набор parts до вызова, либо после, но не смесь.
11. Ошибки в HTTP: `UnknownTable` — 404; `NotLeader` — 409 с адресом лидера; `Syntax`, `UnknownColumn`, `TypeMismatch`, `BadInput`, `TableExists`, `Unsupported` — 400; `Io`, `Internal` — 500.

## Разбор SQL

```
SQL → sqlparser → перевод → SelectQuery / TableDefinition → планировщик → QueryPlan → выполнение
```

Свой Expr нужен обязательно. Если передавать в storage Expr из sqlparser, от sqlparser начнут зависеть storage и types, а хранилищу придётся разбирать выражения, рассчитанные на весь SQL.

Отдельного Statement как сущности нет. Вместо него в query есть функция перевода, которая из AST sqlparser делает `SelectQuery` (плоская структура: колонки, таблица, WHERE, GROUP BY, ORDER BY, LIMIT), `TableDefinition` для CREATE или имя таблицы для DROP и OPTIMIZE. Перевод один раз проходит вложенный AST sqlparser и отказывает во всём неподдерживаемом с ошибкой `Unsupported`. При обновлении sqlparser ломается только он.

## Литералы и типы

Проблема: в `WHERE event_date = '2026-10-01'` после разбора SQL справа стоит строка, а колонка — Date. Сравнить их `Value::compare` не может, и без договорённости индекс не сработал бы как раз на демо.

**Договорённость.** Планировщик (блок B) один раз, при построении плана, приводит литерал к типу колонки, с которой тот сравнивается (=, !=, <, <=, >, >=), через `Value::cast`. В `ScanRequest.predicate`, в `may_match` и в исполнитель литералы попадают уже нужного типа.

Литералы из SQL до приведения:
- число без точки, которое помещается в i64, — Int64; больше — UInt64;
- число с точкой или экспонентой — Float64;
- строка в кавычках — String.

Что разрешает `Value::cast`:

| Из | В | Когда |
|---|---|---|
| String | любой тип | если строка разбирается `Value::parse`: `'2026-10-01'` → Date, `'42'` → Int64 |
| Int64 | UInt64 | если не отрицательное |
| Int64, UInt64 | Float64 | если представимо точно (до 2^53) |
| UInt64 | Int64 | если помещается |
| Float64 | Int64, UInt64 | если без дробной части: `2.0` → `2`, а `2.5` — нет |
| Date | DateTime | всегда, полночь |

Если привести нельзя:
- строка к Date или числу (`'abc'`) — ошибка `TypeMismatch`;
- число со смыслом, который меняется при приведении (`id > 2.5` при Int64-колонке, `x > -1` при UInt64), — литерал остаётся как есть, Query сравнивает по своим правилам для чисел, а `may_match` на разных типах отвечает «может совпасть». Запрос работает, просто без отсечения.

Форматы даты одни и те же везде: в SQL, во входных CSV/TSV/JSON и в выводе. Date — `YYYY-MM-DD`; DateTime — `YYYY-MM-DD hh:mm:ss` (при вводе также с `T` или без времени), время в UTC. Поэтому разбор полей при INSERT (блок C) тоже идёт через `Value::parse`, а вывод — через `Display`.

Арифметика между колонками (`a + b` для Int64 и Float64 и т.п.) — внутреннее дело блока B.

## Агрегатные функции

| Функция | Аргумент | Результат | На пустом входе |
|---|---|---|---|
| count() и count(col) | любой или без аргумента | UInt64 | 0 |
| sum(col) | Int64, UInt64, Float64 | того же типа | 0 |
| min(col), max(col) | любой | того же типа | значение по умолчанию для типа |

- count() и count(col) пока работают одинаково, потому что NULL нет.
- sum от String, Date и DateTime — ошибка `TypeMismatch`. При переполнении целых — перенос без ошибки, как в ClickHouse.
- Значение по умолчанию для min/max: 0 для чисел, пустая строка, 1970-01-01 для дат. Так делает ClickHouse без Nullable.
- Запрос без GROUP BY всегда возвращает одну строку, даже по пустой таблице. Запрос с GROUP BY по пустой таблице возвращает ноль строк.
- У каждой функции одинаковый набор операций: создать пустое состояние, обновить колонкой, слить с другим состоянием, получить результат. Слияние нужно для агрегации по нескольким блокам параллельно.
- avg — по желанию в конце: её состояние — пара (сумма, количество).

## Репликация

Делаем в следующей лабе. Модель продумываем сейчас, чтобы под неё не пришлось переделывать storage и сервер.

**Модель.** Одна нода — лидер, остальные — реплики. Кто лидер, задано в конфиге, выборов нет. Запись (INSERT, CREATE, DROP, OPTIMIZE) принимает только лидер, реплика на неё отвечает `NotLeader` с адресом лидера. Читать можно с любой ноды; реплика может отставать на интервал синхронизации.

**Единица репликации — part.** Parts неизменяемы, и создаёт их только лидер, поэтому имя part однозначно определяет его содержимое. Значит, состояние таблицы — это просто набор имён её parts.

**Синхронизация.** Раз в `sync_interval_ms` реплика делает один проход:
1. Сверяет список таблиц с лидером: создаёт недостающие, удаляет лишние, пересоздаёт те, у которых изменилось описание.
2. Для каждой MergeTree-таблицы сравнивает свой набор parts с набором лидера, скачивает недостающие и одним вызовом `sync_parts` добавляет их и убирает лишние.

Merge делает только лидер. Реплика получает смёрженный part как новый и в том же атомарном вызове убирает исходные, поэтому при чтении не бывает дублей.

**Почему так, а не журнал операций.** Журнал не нужно хранить, обрезать и восстанавливать. Отставшая или перезапущенная реплика догоняет лидера одним проходом. Цена — каждый проход запрашивает список parts каждой таблицы; для лабы это нормально.

Таблицы Memory не реплицируются: на реплике такая таблица создаётся пустой.

**Транспорт.** HTTP между нодами на том же сервере. На схеме указан gRPC, но HTTP проще, а при желании потом меняется одна реализация `Peer`. Эндпоинты:
- `/ping`;
- `/replica/tables` — список таблиц;
- `/replica/parts?table=t` — список parts;
- `/replica/part?table=t&name=p` — файлы одного part.

**Что уже есть в коде:**
- методы репликации в `Table`, по умолчанию возвращают `Unsupported`;
- `PartData`, `Peer`, `DbError::NotLeader`;
- `LocalPeer` — Peer поверх каталога другой ноды в том же процессе. С ним репликацию можно тестировать двумя каталогами в одном тесте, без сети;
- крейт replication: `NodeConfig` (id ноды, адрес, роль, интервал) и сигнатура `sync_once(local, leader)`, пока возвращает `Unsupported`.

**Кто что делает в следующей лабе:** A — `export_part` и `sync_parts`; B — `sync_once`; C — HTTP-реализация `Peer`, эндпоинты `/replica/*`, фоновый поток синхронизации, проверка роли на запись.

**Не делаем:** автоматический выбор нового лидера (при падении лидера меняем конфиг вручную), шардирование, распределённые запросы.

**Открытые вопросы:**
- Отвечать на INSERT сразу или ждать, пока part скачают реплики? Проще сразу.
- В каком виде передавать part по HTTP: архив одним ответом или JSON с base64?
- Отправлять запись с реплики на лидера самой нодой, а не возвращать ошибку клиенту? Удобно, но можно позже.

## Заглушки

В `types::testing` лежит то, на чём каждый работает с первого дня:
- MemTable и MemTableFactory — таблица в памяти. Остаются и дальше как engine Memory;
- MemCatalog — каталог в памяти, любую таблицу создаёт как MemTable;
- StubQueryEngine — понимает только `SELECT * FROM t`;
- `may_match` — всегда отвечает «может совпасть»: корректно, но ничего не отсекает, пока B не напишет настоящий;
- LocalPeer — для тестов репликации.

# Часть 2. Блоки

## Блок A. Storage

Тесты пишутся прямо на Block, другие блоки не нужны. Результат scan удобно сравнивать с MemTable на тех же данных.

### Устройство part

Таблица делится на parts, part — на колонки, колонка — на гранулы.

```
data/hits/
├── table.json                   ← счётчик номеров вставок
└── all_1_1_0/                   ← part: результат одного INSERT, неизменяемый
    ├── part.json                ← строки, гранулы, колонки, кодек, min/max ключа
    ├── primary.idx              ← ключ первой строки каждой гранулы
    ├── user_id.bin              ← данные колонки, гранула за гранулой, каждая сжата отдельно
    ├── user_id.mrk              ← где в .bin начинается каждая гранула
    ├── url.bin
    └── url.mrk
```

**Part** — то, что дал один INSERT. Данные внутри отсортированы по ORDER BY. После записи part не меняется: merge создаёт новый, старые удаляются.

**Гранула** — `index_granularity` строк подряд (по умолчанию 8192, последняя может быть короче). Это минимальная единица чтения: индекс указывает на гранулы, а не на строки. На миллион строк получается 123 гранулы, и индекс целиком лежит в памяти.

Главное упрощение по сравнению с ClickHouse: одна гранула одной колонки = один сжатый кусок. Поэтому метка — одно смещение. В ClickHouse сжатые блоки больше гранулы, метка состоит из двух смещений, а размер гранулы подстраивается под данные; нам это не нужно.

### Формат файлов

Всё в little-endian (`to_le_bytes` / `from_le_bytes`), без внешних библиотек, кроме кодеков.

**Кодирование значений** (одна гранула одной колонки → байты):

| Тип | Байты |
|---|---|
| Int64, UInt64, Float64, DateTime | по 8 байт на значение, подряд |
| Date | 4 байта (i32) |
| String | на каждую строку: длина (u32), затем байты UTF-8 |

При декодировании число строк берётся из метки, и проверяется, что байтов ровно столько, сколько нужно. Если не сходится — файл битый, ошибка `Internal`, без паники.

**`<col>.bin`** — последовательность сжатых рамок, по одной на гранулу:

```
[codec: u8][размер сжатых данных: u32][размер исходных: u32][сжатые данные]
```

Кодек записан в каждой рамке, чтобы part читался, даже если настройка таблицы потом поменялась. Для None данные лежат как есть, с тем же заголовком.

**`<col>.mrk`** — на гранулу ровно 12 байт: смещение рамки в `.bin` (u64) и число строк (u32). Метка гранулы `i` лежит по смещению `i * 12`.

**`primary.idx`** — для каждой колонки ключа подряд её значения в первых строках гранул, тем же кодированием, без сжатия.

**`part.json`** — через serde:

```rust
#[derive(Serialize, Deserialize)]
struct PartMeta {
    format_version: u32,   // при изменении формата старые parts отказываются читаться
    rows: u64,
    granules: u32,
    columns: Vec<ColumnDef>,
    codec: Codec,
    min_key: Vec<Value>,
    max_key: Vec<Value>,
}
```

Весь этот код живёт в отдельном модуле `format`. Остальной storage работает только через него и с байтами напрямую не возится. Тесты модуля: закодировать, раскодировать, сравнить.

### Имена parts

Имя — `all_<min>_<max>_<level>`. Номера берутся из счётчика вставок таблицы: первый INSERT — `all_1_1_0`, второй — `all_2_2_0`. Merge этих двух даёт `all_1_2_1`: диапазон покрывает исходные, уровень на 1 больше. Имена никогда не повторяются, это нужно и для репликации. Счётчик хранится в `table.json`, а при старте сверяется с максимумом из имён parts.

### Запись part

1. Отсортировать Block по ключу ORDER BY.
2. Разрезать на гранулы.
3. Для каждой колонки и каждой гранулы: закодировать, сжать, дописать рамку в `.bin`, смещение — в `.mrk`.
4. Ключ первой строки каждой гранулы — в `primary.idx`; счётчики и min/max — в `part.json`.
5. Всё пишется в `tmp_<name>/`, в конце каталог переименовывается в `<name>/`. Переименование атомарно, поэтому после падения не остаётся полузаписанный part. Каталоги `tmp_*` при старте удаляются.

### Чтение (scan)

1. Отсечение parts: `may_match(predicate, order_by, KeyRange { min: min_key, max: max_key })`; если `false`, part пропускается целиком.
2. Отсечение гранул: то же для каждой гранулы, диапазон — от ключа её первой строки до ключа первой строки следующей гранулы (для последней — до `max_key`). Подряд идущие подходящие гранулы читаются одним диапазоном. Гранул немного (123 на миллион строк), поэтому простой проход по всем достаточно; бинарный поиск — оптимизация на потом.
3. Для каждой нужной колонки: смещения этих гранул из `.mrk`, чтение рамок из `.bin`, распаковка, декодирование.
4. Из гранул собирается Block и отдаётся в поток. Лишние строки внутри гранул отфильтрует Query.

При старте таблица читает для каждого part `part.json`, `primary.idx` и `.mrk` и держит их в памяти. `.bin` читается только во время scan.

### Отсечение и EXPLAIN

Отсечение — одна внутренняя функция: по ScanRequest она возвращает список выбранных parts и диапазонов гранул в каждом. `scan` читает данные по этому списку, `explain_scan` по нему же только считает `ScanStats`. Каждый scan дополнительно пишет свои `ScanStats` в лог через tracing — это пригодится при замерах.

### Шаги

1. Модуль `format`: кодирование колонок, рамки с кодеком None, метки, индекс, `PartMeta`. Тесты «туда и обратно».
2. Кодеки LZ4 и ZSTD.
3. Запись part через временный каталог.
4. Чтение part: нужные колонки, нужный диапазон гранул.
5. Репозиторий parts: список активных, загрузка при старте, атомарная замена набора. Старый part удаляется с диска, когда его отпустил последний читатель: part лежит в `Arc`, scan держит копию, удаление — в `Drop`.
6. insert: один INSERT — один part.
7. scan без индекса: все parts, все гранулы.
8. Отсечение parts и гранул через `may_match`. Внутри storage функция проверки — параметр (по умолчанию `may_match`), поэтому в тестах можно подставить свою, например «ключ больше 1000», и проверить отсечение, не дожидаясь B. Когда B сделает настоящий анализ, отсечение заработает без изменений в storage.
9. `explain_scan` поверх той же функции отсечения, что и scan, плюс запись `ScanStats` каждого scan в лог.
10. Merge: политика выбирает несколько соседних мелких parts, слияние отсортированных данных (на каждом шаге — строка с наименьшим ключом) записывается тем же кодом, что и INSERT. Пока только по OPTIMIZE.
11. Тесты: записанное читается обратно; отсечение действительно пропускает гранулы (считать прочитанные); после рестарта данные на месте.

Позже: контрольные суммы на рамку (crc32fast). Ловят повреждённые файлы и пригодятся при репликации для проверки скачанного part.

Под репликацию сейчас:
- part полностью лежит в своём каталоге, ничего про него не хранится снаружи;
- имена parts уникальны и не переиспользуются, в том числе после merge;
- атомарная замена набора parts из шага 5 — сразу в виде, пригодном для `sync_parts`: добавить несколько и убрать несколько за один раз;
- `parts()` реализовать сразу, это просто список.

В следующей лабе: `export_part` (прочитать файлы каталога) и `sync_parts` (записать полученные parts во временные каталоги, переименовать, атомарно обновить набор).

## Блок B. Query

Работает на MemCatalog и MemTable.

1. Подключить sqlparser с диалектом ClickHouse и написать перевод его AST в SelectQuery, TableDefinition или имя таблицы. Всё неподдерживаемое — ошибка `Unsupported`.
2. Тесты перевода: SQL → ожидаемая структура, плюс понятные ошибки.
3. Вычисление выражений над Block: арифметика, сравнения, AND/OR/NOT. Литералы при сравнении с колонкой приводятся по правилам из раздела «Литералы и типы»; правила для арифметики между колонками (Int64 + Float64 и т.п.) решить здесь.
4. Планировщик: проверяет колонки по схеме из Catalog, приводит литералы к типам колонок (`Value::cast`), выводит типы результата, передаёт WHERE в `ScanRequest.predicate` и запрашивает только нужные колонки.
5. Анализ условий для отсечения: `may_match` в `types::key_condition`. Сравнения первой колонки ключа с литералом (=, <, <=, >, >=, в том числе литерал слева: `5 < id`), AND, OR. Всё остальное — `true`. Значения сравниваются через `Value::compare`. Тесты: таблица «условие, диапазон → ожидаемый ответ», отдельно — что на неподдерживаемых условиях ответ `true`. Это нужно storage к этапу 2, поэтому делать после шага 4.
6. Трансформы: Filter, Project, Limit.
7. Исполнитель: собирает scan и трансформы в один поток блоков.
8. QueryEngine: перевод → план → выполнение; для DDL и OPTIMIZE — вызовы Catalog и Table.
9. Агрегаты count, sum, min, max по правилам из части 1, затем GROUP BY. Агрегатам и сортировке нужен сигнал конца потока: у трансформа есть `finish()`.
10. Sort.
11. EXPLAIN. `EXPLAIN SELECT ...` sqlparser разбирает сам. Query строит план, для узла Scan вызывает `Table::explain_scan` и возвращает обычный `QueryOutput::Rows` с одной строковой колонкой `explain` — по строке на узел плана:
    ```
    Limit 10
      Aggregate by user_id: count()
        Filter event_date = '2026-10-01'
          Scan hits [event_date, user_id]
            parts: 2 / 7, granules: 14 / 861, rows: 114688 / 7000000
    ```
    Для сервера и Swagger это обычный результат SELECT, отдельный эндпоинт не нужен. Нужен для демо.

Под репликацию сейчас: ничего специального. Запросы читают локальные данные, а запись на реплике отсекает сервер.

В следующей лабе: `sync_once` в крейте replication. Это чистая логика поверх Catalog, Table и Peer, тестируется двумя каталогами через `LocalPeer` без сети.

## Блок C. Сервер, Catalog, форматы

Работает на MemCatalog и StubQueryEngine, потом подменяет их на настоящие.

1. Catalog: create, drop, get, list под RwLock, фабрики по engine.
2. Сохранение описаний таблиц на диск и открытие таблиц при старте.
3. Разбор входа: CSV, затем TSV и JSONEachRow, из байтов тела запроса в Block по схеме таблицы. Каждое поле разбирается через `Value::parse`, ошибка превращается в `BadInput` с номером строки. Решить: порядок колонок как в схеме или по заголовку; принимать ли в JSON число строкой (`"42"` в Int64-колонку) — `Value::parse` это уже умеет. Если строка не разбирается — весь INSERT падает с номером строки. Тело читается в память целиком; чтение по частям — позже.
4. Форматы вывода: TSV (по умолчанию), CSV, JSONEachRow, Pretty. Значения печатаются через `Display` у Value, чтобы даты выглядели так же, как при вводе.
5. Каркас на axum: `AppState` (каталог, QueryEngine, конфиг ноды), роутер, превращение `DbError` в ответ через `IntoResponse` по таблице кодов из части 1. Вызовы ядра — внутри `spawn_blocking`.
6. Обработчики по модулям, в таком порядке:
   - `admin.rs`: `GET /ping`, `GET /help`;
   - `meta.rs`: `GET /tables`, `GET /tables/{name}` (describe: схема, engine, ORDER BY, а также число parts и строк из `explain_scan` с пустым запросом), ответ в JSON;
   - `insert.rs`: `POST /insert/{table}?format=CSV`, тело — данные;
   - `query.rs`: `POST /query?format=TSV`, тело — SQL.
   Стриминг больших ответов — позже.
7. Swagger: utoipa-описание всех эндпоинтов, страница `/swagger-ui`. Чтобы Swagger был удобен для демо:
   - у `/query` тело — `text/plain` с примером SQL;
   - у `/insert/{table}` тело — `application/octet-stream`, тогда Swagger показывает кнопку выбора файла;
   - параметр `format` — enum, Swagger покажет выпадающий список.
8. Конфиг: адрес, путь к данным, размер гранулы, кодек; флаги командной строки (clap) и `config.toml`.
9. Сквозные тесты: поднять сервер, CREATE → INSERT → SELECT. Этот же человек отвечает за сборку всех частей вместе.
10. Генератор тестовых данных: CSV на миллион строк с ключом, по которому видно отсечение (например, `event_date`, `user_id`). Нужен всем с этапа 2.
11. Замеры: запрос по ключу против полного скана, вставка, OPTIMIZE; время и число выбранных гранул (из EXPLAIN).
12. Демо-скрипт на bash с curl по сценарию из части 1, плюс README: как собрать, запустить, открыть Swagger.
13. CI: fmt, clippy, тесты на каждый PR.

Пример обработчика, чтобы было понятно, сколько здесь своего кода:

```rust
async fn insert(
    State(app): State<AppState>,
    Path(table): Path<String>,
    Query(params): Query<InsertParams>,   // ?format=CSV
    body: Bytes,
) -> Result<String, ApiError> {
    tokio::task::spawn_blocking(move || {
        let table = app.catalog.get_table(&table)?;
        let block = parse_input(params.format, &body, &table.definition().schema)?;
        table.insert(block)
    })
    .await??;
    Ok("Ok.\n".into())
}
```

Под репликацию сейчас:
