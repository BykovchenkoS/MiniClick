# Дизайн репликации MiniClick (лабораторная №4)

Статус: основная часть реализована. `TableId`, методы каталога, адресация
`Peer` по id, `sync_once`, `/replica/*`, роли, фоновый цикл и запрет записи
на реплику внедрены. Реплика проверяет `cluster_id` и ожидаемый `leader_id`
до любых изменений каталога. Вне текущей реализации остались авторизация/TLS,
failover и выборы лидера; строки `Memory`-таблиц не реплицируются,
их описания создаются на реплике пустыми.

## 1. Цель и границы

- Один узел-лидер принимает запись (CREATE/DROP/OPTIMIZE/INSERT) и владеет
  актуальным состоянием.
- Реплики только читают и периодически подтягивают состояние лидера.
- Синхронизация асинхронная, pull-модель, eventual consistency.
  Между циклами реплика может отдавать устаревшие данные.
- Согласованность обеспечивается по таблицам независимо. Общей транзакции
  на несколько таблиц нет.
- В рамках этой лабораторной реплицируются данные `MergeTree`.
  У `Memory` нет parts: описания создаются на реплике, строки не переносятся.
  Это соответствует исходному заданию: Memory-таблица на реплике пустая.
- Вне объёма: выборы лидера, автоматический failover, мультимастер,
  кворумная запись, chained replication, авторизация и TLS.
- Шардирование не реализуется сейчас, но дизайн не должен ему мешать
  (см. раздел 12).

## 2. Исходное состояние

Уже подготовлено:

- `types::Peer` — интерфейс чтения состояния лидера (`crates/types/src/interfaces.rs:93`).
- `types::Catalog` — каталог таблиц (`crates/types/src/interfaces.rs:108`).
- `types::Table::{parts, export_part, sync_parts}` — хуки репликации,
  реализован только `parts` у `MergeTree` (`crates/storage/src/table/mod.rs:139`).
- `types::PartData` — имя part и его файлы (`crates/types/src/interfaces.rs:85`).
- `replication::{Role, NodeConfig, SyncReport, sync_once}` — заготовки
  (`crates/replication/src/lib.rs`).
- `DbError::NotLeader { leader }` и HTTP-код 409 (`crates/types/src/error.rs:19`,
  `crates/server/src/error.rs:34`).
- `DiskCatalog` уже хранит уникальный `id` (UUID) для каждой созданной таблицы
  (`crates/catalog/src/lib.rs:14`, генерация на `:194`).
- `types::testing::{MemCatalog, LocalPeer}` — реализации для тестов.

Пробелы: `Peer` не передаёт идентичность таблицы, `Catalog` не умеет
создавать таблицу с заданным id и искать таблицу по id, `sync_once` —
заглушка, сетевого `Peer` и фонового цикла нет, запись на реплику не
отклоняется.

## 3. Модель и гарантии

Состояние кластера для реплики:

1. Набор таблиц: `(TableId, TableDefinition)`.
2. Для каждой `MergeTree`-таблицы: набор активных parts (имён).

Реплика приводит своё состояние к состоянию лидера повторяемой сверкой.
Каждый цикл идемпотентен: повторный запуск без изменений на лидере не меняет
данные реплики.

Гарантии:

- Реплика не смешивает данные разных жизненных циклов таблицы с одним именем.
- Реплика не устанавливает частично скачанный набор parts.
- При недоступности лидера реплика не удаляет и не меняет локальные данные.
- После падения и рестарта реплика догоняет лидера обычным циклом.
- Чтение на реплике видит либо старый, либо новый набор parts таблицы,
  но не смесь (обеспечивается атомарным `sync_parts`).

Не гарантируется: линейная согласованность между таблицами, свежесть чтения
в пределах интервала синхронизации, сохранность записи при падении лидера.

## 4. Идентичность таблицы

### 4.1 Проблема

`DiskCatalog` присваивает таблице UUID при CREATE и хранит его в
`catalog.json`, но наружу отдаёт только `TableDefinition`. `Peer::list_tables`
и `Catalog::list_tables` возвращают описания без идентичности. Этого
недостаточно:

- DROP + CREATE с тем же именем и той же схемой создаёт новую таблицу,
  но по `TableDefinition` она неотличима от старой.
- Нумерация parts начинается заново (`all_1_1_0`), поэтому имена старых
  parts могут совпасть с именами новых при другом содержимом.
- Сверка «по имени и схеме» сохранила бы старый part с тем же именем и
  не скачала бы новый, либо получила бы пересечение диапазонов.
  В обоих случаях это порча данных.

### 4.2 Решение

Ввести `types::TableId` — непрозрачный идентификатор таблицы, равный UUID
из каталога создавшей её ноды. Идентификатор:

- присваивается один раз при CREATE и не меняется до DROP;
- сохраняется в `catalog.json` и переживает рестарт;
- уникален в пределах кластера (UUID);
- не входит в `TableDefinition`, то есть не является частью пользовательской
  схемы и SQL.

Реплика создаёт локальную таблицу с id лидера. Тогда локальный id и id лидера
сравниваются напрямую, отдельная таблица соответствия «id лидера ↔ локальный id»
не нужна. Именно этот id используется во всех операциях сверки и в протоколе
`Peer`.

### 4.3 Почему не другие варианты

- Добавить `id` в `TableDefinition`: идентичность попадёт в SQL-схему и в
  `table.json` как пользовательское поле, его придётся заполнять в Query и
  игнорировать при создании. Это смешивает метаданные каталога и определение
  таблицы.
- Сравнивать только схему и parts: не отличает пересоздание с той же схемой;
  сравнение содержимого частей требует чтения всех данных и всё равно
  неоднозначно.
- Хранить на реплике отдельный sidecar-файл соответствия id: появляется
  второе состояние, которое надо согласованно обновлять с `catalog.json`
  при DROP/CREATE и падениях. Лишняя сложность без выгоды.

### 4.4 Сценарий DROP + CREATE с тем же именем

1. Лидер: таблица `hits` имеет id `A`.
2. `DROP TABLE hits`; затем `CREATE TABLE hits ...`. Новая таблица получает
   id `B` и новый пустой каталог данных.
3. Реплика в следующем цикле видит у лидера `(hits, B)`, локально — `(hits, A)`.
   Так как `A != B`, реплика делает `drop_table("hits")` и
   `create_table_with_id(def, B)`. Все parts старого жизненного цикла `A`
   удаляются вместе с таблицей.
4. Затем сверяются parts уже для id `B`.

Если реплика попала в промежуток между DROP и CREATE, лидер вообще не
содержит `hits`, и реплика удалит локальную таблицу. После CREATE следующий
цикл создаст её заново. В любой момент данные не смешиваются; возможен лишь
период, когда таблица на реплике отсутствует.

### 4.5 Окна падения

- Падение между локальными DROP и CREATE оставляет таблицу отсутствующей.
  Следующий цикл создаст её с id лидера. Смешивания нет.
- Если каталог не смог удалить старый каталог данных сразу, это не мешает
  CREATE, потому что новая таблица получает другой UUID-каталог. Остатки
  удаляются существующей очисткой `DiskCatalog`.

## 5. Предлагаемые изменения контрактов

Изменения общих интерфейсов требуют согласования, по `AGENTS.md`.

### 5.1 `types`: новые типы

```rust
/// Идентификатор таблицы, выданный каталогом при CREATE.
/// Для остальных подсистем непрозрачен и сравнивается на равенство.
#[derive(Debug, Clone, PartialEq, Eq, Hash, PartialOrd, Ord, Serialize, Deserialize)]
#[serde(transparent)]
pub struct TableId(String);

impl TableId {
    pub fn new(value: impl Into<String>) -> Self;
    pub fn as_str(&self) -> &str;
}

/// Таблица с идентичностью. Используется Catalog и Peer.
#[derive(Debug, Clone, PartialEq, Eq, Serialize, Deserialize)]
pub struct TableEntry {
    pub id: TableId,
    pub definition: TableDefinition,
}
```

`types` не получает зависимость от `uuid`: формат id проверяет каталог,
который его выдаёт. Остальные подсистемы воспринимают `TableId` как
непрозрачное значение.

### 5.2 `types::Catalog`: три метода

```rust
pub trait Catalog: Send + Sync {
    // ... существующие методы без изменений ...

    /// Все таблицы с идентичностями, отсортированы по definition.name.
    fn table_entries(&self) -> Vec<TableEntry>;

    /// Таблица по идентичности. UnknownTable, если id не активен.
    fn get_table_by_id(&self, id: &TableId) -> Result<Arc<dyn Table>>;

    /// Создать таблицу с заданной идентичностью. Только для репликации.
    /// Для SQL-пользователей недоступно; id проверяет каталог.
    fn create_table_with_id(
        &self,
        definition: TableDefinition,
        id: TableId,
        if_not_exists: bool,
    ) -> Result<()>;
}
```

Реализации:

- `DiskCatalog`: `StoredTable.id` уже существует. `create_table` продолжает
  генерировать UUID, но делегирует общей установке таблицы вместе с
  `create_table_with_id`. Метод с id проверяет канонический формат UUID,
  уникальность id и обрабатывает остатки неактивного каталога.
- `MemCatalog`: хранит id рядом с таблицей. Генерирует простые стабильные
  идентификаторы для `create_table` (например, `mem-<counter>`) и принимает
  заданный id в `create_table_with_id`. Позволяет тестировать контракт без
  диска. Данные `MemTable` не реплицируются.

`get_table_by_id` у `DiskCatalog` ищет запись по `stored.id` под одной
read-блокировкой, поэтому DROP/CREATE не может подменить таблицу между
проверкой id и получением объекта.

### 5.3 `types::Peer`: адресация по id

```rust
pub trait Peer: Send + Sync {
    fn ping(&self) -> Result<()>;
    fn list_tables(&self) -> Result<Vec<TableEntry>>;
    fn list_parts(&self, table: &TableId) -> Result<Vec<String>>;
    fn fetch_part(&self, table: &TableId, part: &str) -> Result<PartData>;
}
```

Меняется возвращаемое значение `list_tables` и параметры операций с parts:
вместо имени передаётся идентичность. Это принципиально: между вызовами
`list_tables` и `fetch_part` лидер может выполнить DROP + CREATE, и запрос
по имени попал бы в другой жизненный цикл. Запрос по id либо относится
к нужной таблице, либо возвращает «id не активен».

`LocalPeer` обновляется: `list_tables` берёт `catalog.table_entries()`,
операции с parts используют `catalog.get_table_by_id()`.

### 5.4 Потоковая установка parts с сохранением прежних сигнатур

Сигнатуры `Table::{parts, export_part, sync_parts}` сохранены.
Добавлен метод с реализацией по умолчанию:

```rust
fn sync_parts_stream(
    &self,
    add: &mut dyn Iterator<Item = Result<PartData>>,
    remove: &[String],
) -> Result<()>;
```

Базовая реализация собирает данные и вызывает прежний `sync_parts`, что
сохраняет совместимость реализаций Table. MergeTree переопределяет метод:
потребляет итератор по одной части, записывает её на диск и только затем
получает следующую. Ошибка итератора отменяет весь импорт. `sync_parts`
у MergeTree вызывает тот же механизм для переданного Vec.

Таблица не обязана знать свой id: её выбирает каталог, а экспорт и установка
parts работают в рамках конкретного объекта таблицы.

`PartData { name, files, checksum }` остаётся прежним. Идентичность part — пара
`(TableId, имя part)`; содержимое однозначно определяется именем внутри
одного жизненного цикла таблицы.

## 6. Сверка таблиц

`replication::sync_once(local, leader, expected_identity)`:

1. `leader.ping()` и `leader.list_tables()`. Любая ошибка здесь фатальна для
   цикла: локальные данные не меняются.
2. `local.table_entries()`.
3. Для каждой удалённой таблицы, включая Memory:
   - нет локальной с таким именем → `create_table_with_id(def, id, false)`;
   - есть локальная с тем же id → сравнить `TableDefinition`
     (см. раздел 8);
   - есть локальная с другим id → `drop_table(name, true)`, затем
     `create_table_with_id(def, id, false)`.
4. Для каждой локальной таблицы, которой нет у лидера →
   `drop_table(name, true)`.
5. Для каждой `MergeTree`-таблицы лидера выполнить сверку parts (раздел 7).

Для Memory сверяется только описание и идентичность, parts не запрашиваются.
При смене движка с Memory на MergeTree или обратно действует та же смена
жизненного цикла. Каталог реплики выделенный: самостоятельные локальные
таблицы не сохраняются при сверке, если их нет на лидере.

Ошибка по одной таблице не прерывает цикл: она логируется, увеличивает
счётчик неуспехов в `SyncReport`, остальные таблицы обрабатываются.
`SyncReport` можно расширить полем `failed_tables` (тип живёт в
`replication`, не является общим контрактом).

## 7. Сверка parts

### 7.1 Идентификация активных parts

- Источник истины — `leader.list_parts(&id)`; у `MergeTree` это атомарный
  снимок активного набора в `PartRepository::snapshot`
  (`crates/storage/src/repository/mod.rs:196`).
- Локальный набор — `table.parts()`.
- `add = target \ local`, `remove = local \ target`.

Parts неизменяемы, а внутри одного `TableId` имена не переиспользуются:
номер вставки монотонно растёт, merge создаёт part с новым уровнем и
диапазоном, а после DROP + CREATE меняется `TableId`. Поэтому сверка
множеств по именам корректна и идемпотентна: повторный цикл без изменений
даёт пустые `add` и `remove`.

### 7.2 Атомарная установка

`table.sync_parts_stream(add, remove)`:

1. Лениво получить очередной part, проверить SHA-256, имена и файлы.
2. Записать его во временный каталог `tmp_*`, выполнить `fsync`,
   переименовать в `all_*`, но не включать в активный набор. После записи
   содержимое освобождается из памяти; повторить для следующего part.
3. Одним вызовом `PartRepository::replace` опубликовать новый активный набор
   (`crates/storage/src/repository/mod.rs:227`). `replace` уже атомарен для
   читателей, проверяет пересечение диапазонов и учитывает снимки,
   удерживаемые читателями.

Если скачивание или проверка хотя бы одного part не удались, публикация
не выполняется: частично установленного набора не бывает. Подготовленные каталоги
удаляются, активный набор не меняется. При рестарте `PartRepository::open`
сам удаляет `tmp_*` и неактивные `all_*`. Контрольная сумма покрывает имена,
длины и содержимое всех файлов, поэтому порча `.bin` обнаруживается до
публикации.

### 7.3 Экспорт на лидере

`export_part(name)`:

- получает снимок репозитория и находит `Arc<DataPart>` по имени;
- если part уже не активен, возвращает ошибку «part не активен»;
- читает файлы, удерживая `Arc<DataPart>`, и считает SHA-256 в порядке файлов.

Удержание `Arc` важно: `replace` помечает старый part retired, но файлы
удаляются только при освобождении последнего `Arc` (`DataPart::drop`,
`crates/storage/src/part/mod.rs:430`). Поэтому параллельный OPTIMIZE не удалит
файлы в момент передачи. Старые parts неизменяемы, поэтому читать их
безопасно.

`sync_parts` после записи открывает каждый part через `DataPart::open`,
который проверяет схему, marks, индекс и ключи. Импортированный part
валидируется до публикации.

### 7.4 Конкурентный OPTIMIZE

OPTIMIZE на лидере меняет набор parts: создаёт merged part и удаляет
исходные. Реплика не блокирует лидера и может увидеть любую комбинацию:

- `list_parts` вернул старые parts, затем OPTIMIZE их убрал.
  `fetch_part` по старому part вернёт «не активен» → сверка этой таблицы
  прерывается, следующий цикл увидит merged part и атомарно заменит
  старый набор новым.
- `export_part` успел удержать `Arc` до удаления → реплика получит валидные
  старые parts и установит старый набор. Следующий цикл заменит его на
  merged part.
- OPTIMIZE произошёл между скачиванием частей и `sync_parts` → реплика
  публикует согласованный старый набор; на следующем цикле догоняет.

Во всех случаях временно возможна устаревшая, но целостная версия таблицы.
Смеси старых и новых parts не возникает: `sync_parts` публикует набор
атомарно, а `replace` не допускает пересечения диапазонов.

Если нужно сократить отставание, `sync_once` может повторить сверку таблицы
один раз в том же цикле. Это не обязательно для корректности: периодический
цикл уже обеспечивает сходимость. Без специального признака «retryable»
достаточно считать ошибку table-level и повторить на следующем тике.

## 8. Совместимость схем

- Реплика создаёт таблицу строго по `TableDefinition` лидера, поэтому схема,
  `ORDER BY`, `index_granularity` и codec совпадают.
- Одинаковый `TableId` с разными `TableDefinition` — нарушение инварианта
  (DDL не умеет ALTER, id выдаётся один раз на CREATE). В этом случае
  сверка таблицы завершается ошибкой без изменения данных. Молча
  пересоздавать таблицу нельзя: это могло бы уничтожить данные при
  повреждённых метаданных.
- Каждый импортированный part проверяется `DataPart::open` на совпадение
  схемы с таблицей.

## 9. Ошибки, повторная синхронизация и восстановление

- Недоступен лидер (`ping`/`list_tables`): `sync_once` возвращает ошибку,
  локальное состояние не меняется. Фоновый цикл повторит попытку.
- Ошибка одной таблицы: учитывается в отчёте, остальные таблицы
  синхронизируются.
- Ошибка скачивания/установки parts: таблица не меняется, повтор на
  следующем цикле.
- Рестарт реплики: каталог открывает уже установленные таблицы и parts,
  первый цикл досинхронизирует недостающее.
- Рестарт лидера: id и parts сохраняются в его каталоге и `table.json`,
  поэтому реплика продолжает сверку без специального протокола.
- Идемпотентность: повторный цикл без изменений не создаёт и не удаляет
  ничего.
- Порядок действий в цикле (таблицы → parts) гарантирует, что parts
  устанавливаются только в существующую таблицу нужного жизненного цикла.

## 10. Роль, конфигурация и HTTP

### 10.1 Конфигурация

`NodeConfig` уже содержит `role` и `sync_interval_ms`. Нужно добавить их
разбор в `Config`:

```toml
role = "Replica"          # Leader | Replica
leader_addr = "127.0.0.1:8123"
sync_interval_ms = 1000
```

- Для `Replica` `leader_addr` обязателен и должен разбираться как `SocketAddr`.
- `sync_interval_ms > 0`.
- Для `Leader` `leader_addr` не используется.
- `Role::Replica { leader_addr }` уже есть в `replication`.

### 10.2 Запрет записи на реплике

- `/insert/*` на реплике всегда возвращает `DbError::NotLeader { leader }`
  (HTTP 409).
- `/query` на реплике отклоняет write-SQL до выполнения. Классификацию
  (`CREATE`/`DROP`/`OPTIMIZE` — запись; `SELECT`/`EXPLAIN SELECT` — чтение)
  добавляет крейт `query`, чтобы `sqlparser` не выходил за его границы.
- Чтение (`/query` с SELECT/EXPLAIN, `/tables`, `/tables/{name}`, `/ping`)
  разрешено.
- Реплика не принимает локальные DDL/INSERT, поэтому её состояние меняется
  только синхронизацией. Это упрощает идентичность и сверку.

### 10.3 Фоновый цикл

- Лидер: цикла нет.
- Реплика: цикл выполняется в `spawn_blocking`, `HttpPeer` создаётся один раз
  и переиспользует соединения. Пауза между проходами —
  `sync_interval_ms`; остановка передаётся через канал, `main` дожидается
  завершения фоновой задачи при graceful shutdown.
- `HttpPeer` сохраняет синхронный интерфейс Peer, но исполняет HTTP-запросы
  асинхронным клиентом в своём runtime. Канал остановки передаёт отмену
  через watch: текущий запрос, включая тело ответа, прерывается без ожидания
  сетевого timeout. `sync_once_with_cancel` проверяет остановку до изменений
  и между скачиваниями. Текущая файловая операция завершается; незавершённый
  импорт откатывается. Незавершённые файлы после падения удаляются при старте.
- Ошибки и `SyncReport` логируются через `tracing`; частичный успех
  (`failures > 0`) логируется отдельным предупреждением.

### 10.4 Сетевой протокол `/replica/*`

`Peer` реализуется в крейте `server` (сеть — ответственность сервера), а не в
`replication`, чтобы крейт репликации зависел только от `types`.

Маршруты (только чтение; только на лидере):

| Маршрут | Ответ |
|---|---|
| `GET /replica/ping` | JSON `NodeIdentity` (`cluster_id`, `node_id`) |
| `GET /replica/tables` | JSON `[TableEntry]` |
| `GET /replica/tables/{id}/parts` | JSON `[String]` |
| `GET /replica/tables/{id}/parts/{part}` | бинарный `PartData` |

Ответ частей использует собственный little-endian формат: magic/version,
имя, checksum, число файлов, затем для каждого файла длина имени, длина
данных, имя и данные. Все размеры проверяются с ограничениями; неизвестные и
небезопасные имена отклоняются. Ответ с одним part ограничен 512 МиБ,
`HttpPeer` проверяет `Content-Length` и фактический объём до декодирования.

`HttpPeer` — синхронный клиент; цикл реплики выполняется в `spawn_blocking`,
поэтому клиент создаётся один раз и переиспользуется.
Эндпоинты не требуют авторизации в этой лабораторной; это ограничение
нужно зафиксировать в README.

## 11. Почему это минимально

- Не добавляются новые общие трейты и не дублируются операции `Table`.
- Идентичность — существующий UUID каталога, без нового хранилища и без
  второго файла состояния.
- Сверка не требует логов операций (WAL) и репликации команд: состояние
  таблицы и набор parts уже достаточны и идемпотентны.
- Сетевой слой остаётся в `server`, ядро репликации — чистая функция над
  `Catalog` и `Peer`.
- `PartData` и формат parts не меняются.

## 12. Совместимость с будущим шардированием

- `TableId` — глобально уникальный UUID, а не имя и не «номер шарда».
  Одинаковые имена таблиц в разных шардах не конфликтуют.
- `replication::sync_once` принимает конкретный `Peer` и работает с
  таблицами по id. Это внутренняя функция крейта `replication`, поэтому
  позже можно добавить параметр области синхронизации (список таблиц/шардов)
  без изменения общих контрактов `types`.
- Лидер не хранится глобально в `Catalog`; адрес лидера задаётся конфигом и
  передаётся в `Peer`. Это позволяет позже синхронизировать разные таблицы
  с разными лидерами шардов.
- Шардирование не должно кодироваться в `TableId`, именах parts или
  `PartData`. Маршрутизация запросов по шардам — задача query/server.
- Репликация не привязана к HTTP в ядре: другой транспорт (например, gRPC)
  сможет реализовать `Peer` без изменений `replication`.

## 13. План проверки (для следующих шагов)

- Идентичность: DROP + CREATE с тем же именем и схемой даёт новый id;
  реплика заменяет таблицу и не смешивает parts `all_1_1_0` старого и нового
  жизненного цикла.
- Повторная синхронизация без изменений: `SyncReport` без добавлений и
  удалений, данные не меняются.
- Схема: одинаковый id с другим `TableDefinition` — ошибка таблицы,
  локальные данные не тронуты.
- Parts: экспорт → импорт сохраняет все строки; `sync_parts` не теряет и не
  дублирует данные; неверный набор не публикуется.
- Конкурентный OPTIMIZE: лидер меняет набор parts во время сверки; реплика
  сходится к merged part без потерь и дублей.
- Недоступный лидер: реплика не удаляет таблицы и не меняет parts.
- Рестарт реплики: данные и каталог сохраняются, досинхронизация работает.
- Запись на реплику: `/insert` и write-SQL возвращают 409 с адресом лидера.
- Сквозной процесс: лидер + реплика, CREATE/INSERT/OPTIMIZE на лидере,
  SELECT на реплике, рестарт реплики.

## 14. Риски и ограничения

- Eventual consistency: чтение с реплики может отставать.
- Нет авторизации/TLS на `/replica/*`; эндпоинты нельзя выставлять в
  недоверенную сеть.
- Нет автоматического failover: при падении лидера реплика становится
  только для чтения устаревших данных.
- Реплика зеркалит весь каталог одного лидера. Для узла с несколькими
  шардами потребуется область синхронизации (раздел 12).
- Передача part защищена SHA-256: `PartData.checksum` покрывает имена, длины
  и содержимое файлов, импорт проверяет её до публикации. Это защищает от
  порчи данных при передаче, но не от узла, который намеренно подменил и
  файлы, и контрольную сумму.
- Удаление локальных таблиц, которых нет у лидера, безопасно для выделенной
  реплики, но при будущей мультилидерной схеме понадобится ограничение
  области.

## 15. Вопросы для согласования

1. Расширение `types::Catalog` тремя методами (`table_entries`,
   `get_table_by_id`, `create_table_with_id`) и новыми `TableId`/`TableEntry`.
2. Изменение `types::Peer::list_tables` на `Vec<TableEntry>` и адресация
   `list_parts`/`fetch_part` по `TableId` вместо имени.
3. Использование UUID лидера как локального id реплики (рекомендуется)
   против отдельного файла соответствия.
4. Данные реплицируются только у `MergeTree`; Memory создаются пустыми
   согласно исходному заданию.
5. Поведение при одинаковом id и разном `TableDefinition`: ошибка без
   изменения данных (рекомендуется).
6. Контрольная сумма файлов part реализована через SHA-256 и проверяется
   импортом до публикации.
7. Формат конфигурации `role`/`leader_addr`/`sync_interval_ms`.
8. Отсутствие авторизации и TLS на `/replica/*` в этой лабораторной.
9. Разрешать ли `/replica/*` на реплике (для будущего chained replication)
   или только на лидере.
