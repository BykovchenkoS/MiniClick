# Репликация MiniClick и демонстрация в Docker

## Соответствие конспекту

В конспекте лекции перечислены схемы с одним ведущим, несколькими ведущими
и без ведущего. MiniClick реализует первый вариант: один Leader принимает
INSERT, CREATE, DROP и OPTIMIZE; Replica обслуживает чтение и получает данные
от Leader. Реплики не пересылают запись лидеру, а возвращают HTTP 409 NotLeader.

Назначение ролей и синхронность репликации — независимые решения.
В MiniClick роль задаёт оператор через TOML или CLI при запуске процесса.
Ни выборов лидера, ни автоматического повышения реплики нет. Одинаковый
cluster_id объединяет узлы; leader_addr указывает источник, а leader_id —
ожидаемый node_id источника. До изменения каталога реплика проверяет оба
идентификатора. Это защита от ошибки конфигурации, а не аутентификация.
Два узла с role = Leader автоматически не договорятся о единственном лидере.

В лекции разобраны способы передачи изменений. Здесь передаётся
готовое физическое состояние: неизменяемые отсортированные parts MergeTree,
уже сформированные после обработки INSERT или merge. SQL-команды не
переигрываются, журнал WAL между узлами не передаётся. Реплика получает список
таблиц и активных parts, скачивает недостающие и заменяет набор parts таблицы.
Существующие parts повторно скачивать не нужно. Файлы проверяются по SHA-256,
публикация нового набора parts атомарна в пределах таблицы; общей транзакции
для снимка всего кластера нет. Memory-таблицы не реплицируются.

Репликация **асинхронная**: HTTP-ответ об успешном INSERT зависит от записи
на лидере, но не от подтверждения реплики. Реплика самостоятельно опрашивает
лидера с паузой sync_interval_ms между проходами; длительность прохода,
ошибки сети и повторные попытки увеличивают задержку. Одна секунда в конфиге
не является гарантией максимального отставания.

Синхронный вариант потребовал бы включить подтверждение реплики в путь записи:
определить, сколько реплик ждём, что считается подтверждением (например,
устойчивая запись на диск), таймауты и смысл ошибки после локальной фиксации.
Клиент после таймаута может не знать, применился ли INSERT, поэтому потребуются
правила повторов и защита от дублей. Простое уменьшение интервала опроса
не превращает текущую реализацию в синхронную.

Разобранные в лекции проблемы чтения относятся к текущему режиму: сразу после
INSERT реплика может вернуть старые данные. Для чтения своих последних записей
клиент обращается к лидеру; автоматической маршрутизации и сессионных гарантий
на репликах нет. Если лидер безвозвратно потерян до синхронизации, подтверждённые
им последние записи могут отсутствовать у реплики. Чтение сохранённых данных
при недоступном лидере поддерживается; продолжение записи требует другого
механизма управления ролями и здесь не реализовано.

Несколько ведущих, CRDT и кворумы, рассмотренные в лекции,
в эту реализацию не входят. Они не являются обязательными этапами настройки
одного лидера с асинхронной репликой. В проекте также нет шардирования,
gRPC-сервера или распределённого SELECT: gRPC указан в архитектурной схеме
как направление развития. Реальный межузловой транспорт — HTTP /replica/*,
с бинарным форматом MCP1 для parts; контракт клиента — types::Peer.

## Сборка и назначение ролей

Нужны Docker Engine, Docker Compose v2 или новее и Bash для сценария.
Первая сборка требует сети. Dockerfile собирает бинарник в Rust 1.96 на Debian
Bookworm, затем переносит его в отдельный образ без компилятора. Процесс работает
с UID 10001. Общие сигнатуры types и версия sqlparser не меняются.

```bash
docker compose up -d --build --wait
docker compose ps
docker compose logs -f leader replica
```

Один образ запускается с двумя разными конфигурациями:

| Параметр | Leader | Replica |
|---|---|---|
| Конфигурация | deploy/leader.toml | deploy/replica.toml |
| node_id | leader-1 | replica-1 |
| role | Leader | Replica |
| cluster_id | miniclick-demo | miniclick-demo |
| leader_addr | — | leader:8123 |
| leader_id | — | leader-1 |
| Хранилище | leader-data | replica-data |
| Порт на хосте | 8123 | 8124 |

Compose создаёт сеть с DNS-именем leader. В каждом контейнере /data указывает
на собственный именованный volume. Общего каталога данных у узлов нет.
Реплика может запускаться раньше лидера: соединение повторяется в фоне.
Healthcheck /ping проверяет доступность HTTP, а не завершение синхронизации.

Swagger доступен на http://localhost:8123/swagger-ui и
http://localhost:8124/swagger-ui. Если порты заняты:

```bash
MINICLICK_LEADER_PORT=18123 MINICLICK_REPLICA_PORT=18124 docker compose up -d --wait
```

Эти же переменные следует задавать при последующих командах Compose и демо.
Для демонстрации на другом компьютере достаточно репозитория с Dockerfile,
compose.yaml, deploy/*.toml и скриптом; Rust на хосте не нужен.

## Показ преподавателю

```bash
bash scripts/demo-replication.sh
```

Скрипт сам собирает и запускает узлы, создаёт таблицу с уникальным именем,
затем проверяет конкретный состав строк, включая отсутствие дублей:

1. CREATE и INSERT на лидере; на реплике появляются схема и две строки.
2. INSERT на реплике возвращает 409 и не изменяет строки.
3. При выключенной реплике лидер принимает третью строку; после запуска
   реплика догоняет лидера. Это демонстрирует асинхронное подтверждение.
4. При выключенном лидере реплика продолжает возвращать три строки.
5. Реплика перезапускается при выключенном лидере и читает те же три строки
   из собственного volume.
6. Лидер возвращается; проверяются обе копии. Узлы и тестовая таблица остаются
   доступными для ручного SELECT в Swagger.

Ожидание синхронизации проверяет результат запроса, а не полагается на одну
фиксированную задержку. При ошибке скрипт выводит логи и пытается запустить
остановленные узлы. Запуск следует выполнять на демонстрационном кластере:
сценарий временно останавливает оба сервиса, но не удаляет volumes или таблицы.

Остановка с сохранением данных:

```bash
docker compose down
```

Для повторного запуска используйте docker compose up -d --wait. Команда
docker compose down -v удаляет оба хранилища со всеми данными; для обычного
перезапуска она не нужна.

Это два независимых процесса и хранилища на одном хосте. Сбой всего хоста
такая демонстрация не переживает. Авторизации, TLS и автоматического failover
нет; внешние HTTP-порты Compose опубликованы только на loopback хоста.
