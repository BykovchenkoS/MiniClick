# Демо шардирования через Docker и Swagger

Два шарда хранят свою часть таблицы `hits_local` в MergeTree. Координатор
предоставляет логическую таблицу `hits`. Ключ `user_id` направляет чётные ID
на `shard-even`, а нечётные на `shard-odd`. Карта задана в
[`deploy/sharding-coordinator.toml`](../deploy/sharding-coordinator.toml).
Каждый шард сверяет ключи со своим правилом размещения.
[`sharding-even.toml`](../deploy/sharding-even.toml) · [`sharding-odd.toml`](../deploy/sharding-odd.toml)

## 1. Запуск

Запустите стенд из корня репозитория.

```bash
docker compose -f compose.sharding.yaml up -d --build --wait
```

| Узел | Swagger UI |
|---|---|
| Координатор | <http://localhost:8130/swagger-ui/> |
| Шард для чётных ID | <http://localhost:8131/swagger-ui/> |
| Шард для нечётных ID | <http://localhost:8132/swagger-ui/> |

Каждый шаг в Swagger выполняется через **Try it out** и **Execute**. Команды SQL
вставляются в тело `POST /query` с форматом ответа `TSV`.

## 2. Создание физической таблицы

Выполните запрос на **обоих шардах**. Ответ каждого узла будет `200` и `Ok.`.

```sql
CREATE TABLE IF NOT EXISTS hits_local (
    user_id UInt64,
    category String,
    amount Int64
) ENGINE = MergeTree
ORDER BY user_id
SETTINGS index_granularity = 1
```

## 3. Загрузка смешанного блока через координатор

Откройте `POST /insert/{table}` на **координаторе**, укажите `table = hits`
и `format = CSV`. Сохраните эти строки в `hits.csv` и загрузите файл одним
запросом.

```csv
1,news,40
2,news,20
3,blog,55
4,shop,50
5,blog,1
6,news,1000
```

Координатор распределит строки по ключу. Ответ `200` и `Ok.` означает, что оба
шарда подтвердили запись. Повторная загрузка файла добавит дубликаты.
Для TSV укажите `format = TSV` и разделите колонки табуляцией. Для
`format = JSONEachRow` передайте по одному JSON-объекту на строку, например
`{"user_id":1,"category":"news","amount":40}`. Для следующих шагов загрузите
набор из шести строк один раз в любом из форматов.

Локальное размещение можно проверить через `POST /query` на каждом шарде.

```sql
SELECT user_id FROM hits_local ORDER BY user_id
```

Ожидаемые ID на чётном шарде — `2, 4, 6`, на нечётном — `1, 3, 5`.

Чтобы проверить защиту от записи на чужой шард, загрузите
[`sharding-odd.csv`](../deploy/sharding-odd.csv) через `POST /insert/{table}`
на чётном шарде с `table = hits_local`. Запрос вернёт `400`. Повторный
SELECT на чётном шарде вернёт прежние строки.

## 4. Распределённый SELECT

Отправьте запрос на **координатор**, чтобы получить две группы с наибольшей суммой.

```sql
SELECT category, sum(amount) AS total, count() AS n
FROM hits
WHERE user_id < 6
GROUP BY category
ORDER BY total DESC, category ASC
LIMIT 2
```

При однократной загрузке файла результат содержит две строки.

```text
news    60    2
blog    56    2
```

Группа `news` объединяет строки с ID 1 и 2 из разных шардов. Строка с ID 6
отфильтровывается до агрегации.

## 5. EXPLAIN и точная фильтрация

Проверьте отсечение через `EXPLAIN` на **координаторе**.

```sql
EXPLAIN SELECT user_id, category, amount FROM hits WHERE user_id = 4
```

В конце плана указаны ID выбранных шардов и статистика чтения.

```text
shards: [1]
parts: 1 / 1, granules: 2 / 3, rows: 2 / 3 (selected / total; before WHERE)
```

Координатор выбирает чётный шард, и статистика относится к его трём гранулам.
Разреженный индекс оставляет две гранулы, чьи диапазоны могут содержать ключ 4.
Выполните тот же запрос без `EXPLAIN`. Точный `WHERE` вернёт одну строку.

```text
4    shop    50
```

## 6. Метаданные в Swagger

На координаторе выполните `GET /tables`. В списке должна быть таблица
`hits` с движком `Distributed` и колонками `user_id`, `category` и `amount`.
Затем выполните `GET /tables/{name}` с `name = hits`. После одной загрузки
`stats.rows_total` и `stats.rows_selected` равны `6`. Сравните с
`SELECT count() FROM hits` через `POST /query`.

Статистика суммирует полный скан по шардам. При недоступном шарде описание
возвращает HTTP 500 с именем или ID проблемного шарда в ошибке. Список таблиц
по-прежнему показывает `hits`, поскольку схема задана в конфигурации стенда.

## Остановка

```bash
docker compose -f compose.sharding.yaml down
```

Данные в томах сохраняются. После повторного запуска можно сразу выполнить
SELECT и EXPLAIN над уже загруженными строками.

## Фиксированная карта размещения

Шарды упорядочены по числовому ID. Остаток `key % N` задаёт позицию в этом
порядке. Перестановка записей в TOML ничего не меняет. Смена числа шардов,
ключа или соответствия ID и узлов может направить запрос в другое место,
хотя существующие строки всё ещё лежат на прежних шардах.

Координатор и обычные шарды сохраняют карту в `sharding-topology.json`
в своём каталоге данных при первом успешном запуске, даже до первой
записи. Координатор закрепляет имена таблиц, ключи, ID и адреса обычных
шардов или состав и идентификаторы Raft-групп. Обычный шард закрепляет
локальные правила. Участники Raft сохраняют отпечаток локальных правил
в `cluster-identity.json`. Несовместимая конфигурация останавливает
запуск. При запросах координатор также сверяет ключ, ID и полный набор ID
с правилами каждого задействованного физического шарда.

При обновлении используйте новую версию на координаторе и физических узлах.
Первый запуск узла без сохранённой карты нужно делать с исходной конфигурацией.
Защита действует, пока сохранён файл карты вместе с каталогом данных узла.
Система не восстанавливает историю прежнего размещения и не проверяет
содержимое чужого тома по тому же адресу. Точечный запрос проверяет только
те шарды, к которым обращается.

Для другой карты нужна явная миграция. Остановите запись, выгрузите данные,
подготовьте новый стенд с нужной картой, загрузите данные по новому правилу
и проверьте полноту перед переключением клиентов. Сохраняйте исходные тома
до завершения проверки. MiniClick не перераспределяет уже записанные строки.

## Две независимые Raft-группы

У каждого шарда три участника, свой `cluster_id`, свой кворум и отдельные тома.
Координатор ищет лидера каждой группы среди адресов из `raft_shards` и читает
с него после подтверждения кворумом. Все участники одной группы применяют
одинаковое правило размещения строк.

При обновлении предыдущего стенда сначала выгрузите таблицу с одноузлового
нечётного шарда. Новый Raft-шард использует собственные тома, старый том
`miniclick-sharding-raft_shard-odd-data` сохраняется.

```bash
curl -fsS 'http://localhost:8144/query?format=JSONEachRow' \
  --data-binary 'SELECT user_id, category, amount FROM hits_local ORDER BY user_id' \
  --output hits-odd.jsonl
```

На чистом стенде запустите Compose и инициализируйте обе группы.

```bash
docker compose -f compose.sharding-raft.yaml up -d --build --wait
curl -fsS -X POST http://localhost:8141/cluster/init
curl -fsS -X POST http://localhost:8144/cluster/init
```

Инициализация выполняется один раз для каждой группы. При обновлении ранее
настроенного стенда перейдите на новый каталог данных координатора после
остановки записи. Инициализируйте только новую нечётную группу, создайте
таблицу на её лидере и загрузите выгрузку через координатор с форматом
`JSONEachRow`. Данные чётной группы остаются в прежних томах.

| Узел | Сервис | Swagger UI |
|---|---|---|
| HAProxy для распределённых запросов | `coordinator-proxy` | <http://localhost:8148/swagger-ui/> |
| Основной координатор | `coordinator` | <http://localhost:8140/swagger-ui/> |
| Резервный координатор | `coordinator-backup` | <http://localhost:8147/swagger-ui/> |
| Участник Raft 1 | `shard-even-1` | <http://localhost:8141/swagger-ui/> |
| Участник Raft 2 | `shard-even-2` | <http://localhost:8142/swagger-ui/> |
| Участник Raft 3 | `shard-even-3` | <http://localhost:8143/swagger-ui/> |
| Нечётный шард, участник 1 | `shard-odd` | <http://localhost:8144/swagger-ui/> |
| Нечётный шард, участник 2 | `shard-odd-2` | <http://localhost:8145/swagger-ui/> |
| Нечётный шард, участник 3 | `shard-odd-3` | <http://localhost:8146/swagger-ui/> |

1. Через `GET /cluster/status` найдите участника с `role = "Leader"` в каждой
   группе. Проверьте порты 8141–8143 и 8144–8146 отдельно. Выполните DDL из
   шага 2 на обоих лидерах.
2. Через HAProxy загрузите смешанный CSV из шага 3. Убедитесь, что
   `SELECT count() FROM hits` возвращает `6`.
3. Остановите лидера нечётного шарда. В примере это первый участник.

   ```bash
   docker compose -f compose.sharding-raft.yaml stop shard-odd
   ```

4. По `GET /cluster/status` найдите нового лидера нечётной группы и проверьте,
   что `term` и лидер чётной группы прежние. Повторите `SELECT count() FROM hits`
   через координатор. Ответ останется `6`.
5. Загрузите через координатор новый CSV с одной строкой `7,shop,70`.
   `INSERT` вернёт `200`, а запрос `SELECT amount FROM hits WHERE user_id = 7`
   через координатор вернёт `70`. Общий `count()` станет `7`.

Для восстановления остановленного узла выполните `docker compose -f
compose.sharding-raft.yaml start shard-odd`, подставив имя сервиса из шага 3.
Координатор заново ищет лидера для каждого запроса. Если проверка одного из
целевых шардов завершится ошибкой, координатор не начнёт запись. После начала
отправки каждый шард применяет свой блок атомарно. При сбое координатор
прекращает отправку и сообщает о подтверждённых записях и неизвестном
результате, если ответ не позволяет определить исход записи. Подтверждённые
строки сохраняются. Автоматического повтора нет.

## Отказ одного координатора

Оба координатора читают один TOML, подключённый только для чтения. У каждого
свой том с локальным каталогом и сохранённой картой размещения. Строки
логической таблицы `hits` хранятся на шардах. Локальные таблицы
координаторов независимы. Используйте общий адрес для логических таблиц
и создавайте физические таблицы на лидерах шардов.

Для обращения через Swagger откройте <http://localhost:8148/swagger-ui/>.
HAProxy проверяет `GET /ping` на обоих координаторах. После обнаружения
отказа основного новые запросы идут на резервный. Когда основной снова
доступен, новые запросы возвращаются к нему. В ответе HAProxy указывает
выбранный сервис в заголовке `X-MiniClick-Coordinator`.

Прокси не повторяет отправленные запросы. Запрос во время переключения может
завершиться ошибкой. При обрыве ответа на INSERT запись могла примениться
полностью, частично или остаться неприменённой. Если исход неизвестен,
проверьте данные перед повторной вставкой. Для SELECT или INSERT на
Raft-шарде по-прежнему нужен кворум этой группы.

HAProxy остаётся единой точкой отказа для общего адреса. При его отказе
доступны прямые адреса координаторов из таблицы выше. Стенд работает на
одном хосте Docker и проверяет отказ контейнера координатора.

Воспроизводимый сценарий запускается на отдельных временных томах.

```bash
python scripts/demo-sharding-quorum.py --coordinator-failover
```

Сценарий останавливает основной координатор, проверяет переключение HAProxy
и завершает работу лидеров обеих Raft-групп. После выборов он выполняет
SELECT и смешанный INSERT в TSV через резервный координатор. Затем он возвращает
основной координатор, останавливает резервный, отправляет смешанный JSONEachRow
и сверяет итоговый набор строк через общий адрес. Сценарий удаляет временные
контейнеры и тома своего проекта.

## Потеря кворума и восстановление с чистых томов

Из корня репозитория запустите автоматизированный сценарий. Нужны Python 3
и запущенный Docker с Compose.

```bash
python scripts/demo-sharding-quorum.py
```

Сценарий создаёт отдельный проект Compose с чистыми томами и свободными
портами. Он инициализирует обе группы, создаёт таблицу на лидерах и
загружает шесть строк одним смешанным CSV и проверяет HTTP-метаданные `hits`.

Затем сценарий останавливает двух участников нечётной группы, оставляя
её лидера без кворума. Все запросы из таблицы отправляются координатору.

| Запрос | Ожидаемый результат |
|---|---|
| `SELECT amount FROM hits WHERE user_id = 4` | `200`, значение `50` |
| `EXPLAIN SELECT amount FROM hits WHERE user_id = 4` | `200`, строка `shards: [1]` |
| Чтение обоих шардов, в том числе с `LIMIT 1` | `500`, ошибка шарда 2 без строк |
| `GET /tables/hits` | `500`, ошибка шарда 2 без статистики |
| INSERT строки `8,shop,70` | `200` |
| INSERT блока с нечётными ключами `7` и `9` | `502` |
| Смешанный INSERT с ключами `10` и `11` | `502`, обе строки отклонены на предварительной проверке |

После запуска остановленных узлов сценарий сверяет все семь строк.
В наборе должны быть шесть исходных строк и новый ключ `8`. После
рестарта координатора сценарий сверяет строки и HTTP-метаданные. В конце он
удаляет контейнеры и тома своего временного проекта.
