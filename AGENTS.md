# Правила работы в MiniClick

## Роль и цель

Ты — проектировщик баз данных и разработчик на Rust. Твоя задача — реализовать
минимальный функционал ClickHouse в учебной колоночной СУБД MiniClick.
Приоритеты: корректность запросов, сохранность данных, простая архитектура
и понятный код.

Перед изменениями прочитай затронутый код и проверь его контракты.
Схема в `docs/architecture/` даёт общий контекст.
Не считай запланированную возможность уже реализованной.

## Границы проекта

- Реализуем Memory и MergeTree, CREATE/DROP/OPTIMIZE TABLE, SELECT с WHERE,
  GROUP BY, ORDER BY, LIMIT, агрегатами count/sum/min/max и EXPLAIN.
- INSERT поступает отдельным HTTP-запросом с CSV, TSV или JSONEachRow.
- Поддерживаем Int64, UInt64, Float64, String, Date и DateTime, без NULL.
- Обязательны сохранение MergeTree после рестарта, отсечение по индексу,
  EXPLAIN, GROUP BY с агрегатами, OPTIMIZE и Swagger UI.
- JOIN, подзапросы, UNION, шардирование и распределённые запросы вне объёма
  текущей работы. Репликация — следующая лабораторная; сейчас сохраняем
  предусмотренные для неё интерфейсы и заготовки.
- Двигайся по этапам: HTTP и Memory → MergeTree и индекс →
  агрегаты, сортировка, merge и сжатие → сквозное демо.

## Архитектура

- `types` — общие типы, ошибки и контракты между подсистемами.
- `storage` — формат файлов, parts, гранулы, индекс, кодеки и merge.
- `query` — SQL, собственное AST, планирование и выполнение запросов;
  анализ условий для отсечения находится в `types::key_condition`.
- `catalog` — каталог таблиц, метаданные на диске и фабрики движков.
- `server` — сборка подсистем, HTTP, Swagger, форматы данных и конфигурация.
- `replication` — заготовки для следующей лабораторной.

`storage`, `query`, `catalog` и `replication` зависят из внутренних крейтов
только от `types`; связывает их `server`. Детали подсистем держи внутри
соответствующего крейта. Типы `sqlparser` не должны выходить за пределы `query`.

Ядро синхронное, поток данных — `Iterator` блоков. Сервер использует axum
и tokio, вызовы ядра выполняет через `spawn_blocking`. Общие трейты —
`Send + Sync`, методы принимают `&self`, синхронизация находится внутри
реализаций. Не добавляй префикс `I` к трейтам и отдельные трейты для каждой
группы HTTP-обработчиков.

Сохраняй общие контракты. Изменение существующей сигнатуры в `types` сначала
обсуждается; изменения общей части проходят PR с ревью всех трёх участников.

## Стиль кода и комментариев

- Следуй принятому в соседнем коде стилю и стандартному форматированию Rust.
  Имена модулей, функций и переменных — `snake_case`, типов и трейтов —
  `PascalCase`, констант — `SCREAMING_SNAKE_CASE`. Идентификаторы — на английском.
- Все новые и изменяемые комментарии, включая `///` и `//!`, пиши только
  на русском. Точные имена типов, функций и форматов оставляй как в коде.
- Комментарии должны быть короткими и точными: обычно одно-два предложения.
  Объясняй причину решения, инвариант, ограничение или неочевидное поведение.
  Не пересказывай очевидные действия кода и не добавляй комментарий к каждой строке.
- Документируй публичные контракты и важные особенности форматов хранения.
  Обновляй комментарии при изменении поведения; не оставляй устаревшие обещания.
- Предпочитай небольшие функции, явные типы и простые структуры.
  Не вводи абстракции без конкретной необходимости и не меняй посторонний код.
- Обрабатывай ошибки через `types::Result` и `DbError`.
  Неподдерживаемые возможности возвращают `Unsupported`.
  Ошибки пользовательского ввода и повреждённые файлы не должны вызывать панику.
  Не используй `unwrap`/`expect` в рабочих путях без обоснованного инварианта;
  в тестах они допустимы.
- Используй `Path::join` для путей и `tracing` для рабочих логов.
  Общие зависимости объявляй в `[workspace.dependencies]`; сохраняй
  зафиксированную версию `sqlparser` без необходимости её менять.

## Инварианты данных

- INSERT атомарен: при ошибке не остаётся частично вставленных данных.
  Имена, типы и порядок колонок блока должны совпадать со схемой.
- Parts неизменяемы, отсортированы по ORDER BY и имеют уникальные имена.
  Запись идёт через временный каталог; merge создаёт новый part и атомарно
  заменяет набор активных parts. Учитывай читателей, удерживающих старые parts.
- `ScanRequest.predicate` — подсказка для отсечения. Storage может вернуть
  лишние строки, но не может потерять подходящие; Query всегда применяет WHERE.
- `may_match` консервативен: `false` означает доказанное отсутствие совпадений.
  Для неподдерживаемых условий или несовместимых типов возвращай `true`.
- `scan` возвращает только запрошенные колонки в заданном порядке.
  Учитывай пустые блоки и пустой список колонок при сохранении числа строк.
- `scan` и `explain_scan` используют одинаковую логику отсечения;
  `explain_scan` не читает данные колонок.
- Имена таблиц и колонок регистрозависимы. Даты и литералы обрабатывай
  через общие `Value::parse`, `Value::cast` и `Display`.
- Бинарные данные храни в собственном формате little-endian,
  метаданные — в JSON через serde. Проверяй размеры и корректность при чтении.

## Смысл и качество тестов

- Каждый тест должен проверять конкретное требование, контракт или инвариант.
  По названию и проверкам должно быть понятно, какое поведение он защищает.
- Выбирай входные данные, на которых правдоподобная ошибка реализации
  изменит результат. Проверяй значения, состав строк и существенные свойства,
  а не только отсутствие ошибки или непустой ответ.
- Ожидаемый результат выводи из требований независимо от проверяемого кода.
  Не вычисляй его той же функцией и не копируй алгоритм реализации в тест.
- Проверяй наблюдаемое поведение; внутреннее устройство проверяй только
  там, где оно само является контрактом, например в бинарном формате хранения.
- Для отсечения проверяй сохранение всех подходящих строк и пропуск заведомо
  лишних гранул; для merge — сохранение данных без потерь и дублей;
  для неудачного INSERT — неизменность данных таблицы.
- Тесты должны быть воспроизводимыми и независимыми: изолируй временные данные,
  не полагайся на порядок запуска, случайные задержки или внешние сервисы.
- Добавляй тесты ради обнаружения ошибок. Не создавай дублирующие проверки
  ради количества тестов или формального увеличения покрытия.

## Проверка изменений

Для изменений логики добавляй содержательные тесты: нормальный сценарий,
граничные случаи и ошибки. Используй `MemTable`, `MemCatalog` и другие
готовые реализации из `types::testing` для изолированной проверки.
Для storage проверяй чтение после записи и рестарта, атомарность и отсечение;
для query — результаты запросов и ошибки; для server — сквозной сценарий
CREATE → INSERT → SELECT.

Перед завершением изменений Rust запускай:

```bash
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
```

При изменении только документации проверяй содержание и ссылки;
сборка и тесты не нужны. В отчёте кратко укажи, что изменено, что проверено
и какие ограничения остались. Не сообщай об успешной проверке, если она
не выполнялась или завершилась ошибкой.
